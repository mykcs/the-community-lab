## 四层验证，必须逐层过门

### L1 · 内容完整性：全部题目到底有没有

1. 对每一季建立**有编号的权威来源清单**；逐题记录韩文题干、全部韩文选项、选项数量、答题类型、原站顺序、截图/网页位置、抓取核实日期、重用权限与源版本。
2. 只在合法许可下保存、公开原题；权限不明时只记录题号、题型、元数据和出处链接。禁止用模型脑补补齐缺失题目。
3. 交叉核对题数、题号是否连续或明示的非连续编号、重复、缺项、隐藏条件题、原版是否更新。公开页面数量一致**只是必要条件，不是充分条件**。
4. 每道发布题强制「韩文原文在前、中文译文在后」，题干、所有选项和量表都需独立双语审校；否定、条件、程度词与计分极性不能漂移。复核详见 [翻译标准](TRANSLATION-STANDARD.md)。

**验收输出**：两季各一份逐题证据清单和来源许可状态，覆盖率=通过审核的原题数/实际原题数。用户报告的许可覆盖当前公开材料及非营利用途，原件与授权主体未独立核验；目前完成权利核验、韩中人工复核并可标为正式译文的节目原题为 **0/124**，不能用演示题 8/87 或 6/37 表示已复刻百分比。

### L2 · 路径完整性：每个选择会把人带到哪

1. 把原站问卷建模为**有向状态图**：起点、题节点、每个可选答案的转移、返回/修改答案、条件跳题、完成节点、取消或重新开始。
2. 如果官方题数是固定的，也需检查是否存在根据先前答案改变顺序、隐藏题目或提前结束的分支，不能未经验证就假定是线性排列。
3. 为每条边留一个真实原站观察或可靠原始资料的证据；对所有可达节点做图遍历，检测死路、无法到达的题、循环与提前提交。
4. 使用模拟用户或可许可的离线样本做路径覆盖；有指数级选项组合时，先用图覆盖+边界/成对覆盖，再用精确的程序化穷举测试本站的小型演示集。

**验收输出**：原站可达图、每条边的证据以及本网站对应路径的差异清单。2026-10-29 的非提交式真实浏览器走查中，第一季一组临时合成回答从 `1/87` 逐题到 `87/87`，观察到 23 道四选题、64 道六选题且每次进度加一；第二季两组逐题互补的合成回答都到达 `37/37`，37 个题位顺序完全一致且每题均二选。两季均停在末题，没有选最后答案或提交结果。

随后对官方公开客户端资源做了只读静态检查：当前资源为 331,501 字节，SHA-256 `59a67f9d1e0049156bedfe4d61a4cf8511dc8903ba80cf297b6bffad3c2b379e`，与纯元数据索引指纹相符。2026-10-30 00:33 UTC 复查 `thecommunity.co.kr` 当前测试页的 HTML 引用同名 JS 资源；GET 后字节数和 SHA-256 完全相同，因此以下客户端发现适用于这次复核的当前页面 bundle。该 bundle 中，题目列表按季别字符串经确定性 Fisher–Yates 洗牌；答题处理器保存所选题目 ID 与答案，未到末题时只把当前位置加一，不按答案值分支；上一题只将位置减一。因此，**对该资源指纹中的客户端代码与题目数组**，观察到的题序是按季别固定的，客户端题目之间没有答案相关跳题或每次会话随机种子。末题会调用 `POST /api/v1/results`，但本任务没有发出该请求；服务端结果生成、服务端路径和评分仍未验证。

结合静态代码与两季浏览器观察，当前已加载客户端的题目导航边可描述为按季别固定的线性序列，每题各选项都汇合到同一下一题。**这不等于验收整个官方端到端结果路径**：末题提交后的行为、服务端响应、其他版本资源及其题序仍为 **UNKNOWN**，不得将静态代码审阅说成官方计分验证。

额外的第二季 UI 走查：在 `37/37` 使用「上一题」后进度显示 `36/37`；点击相反选项后回到 `37/37`。从测试页返回第二季介绍页，再以空昵称启动，新的答题流程从 `1/37` 开始。没有提交结果。另一次合成操作观察到浏览器本机答案映射在选择后存在，回退并改选后映射内容随之改变；刷新后进度回到 `1/37`，答案映射仍存在，但两个选项均未显示已选。因此，**本机映射会写入且允许更新已观察到，刷新后界面是否恢复选择仍未证实**。以上不涉及服务器保存。

2026-10-29 又进行了一次范围受限的第二季合成点击探测：前 5 次单选前进到 `6/37`；第 6 题交互时浏览器自动化拦截到 `POST https://www.google.com/recaptcha/enterprise/reload`，并在发送前中止。探测没有到达原站 `/api/v1/results`，没有提交结果，也没有尝试绕过 reCAPTCHA。该前缀只观察一条路径，未增加分支／边覆盖；触发反机器人请求后停止，因此全部原站路径仍为 **UNKNOWN**。

### L3 · 结果正确性：答案如何变成分数、标签

**2026-10-30 当前公开 bundle 的结果边界复核：** 对官方页面当前引用的 JS 资源再次只读 GET，资源为 331,501 字节，SHA-256 `59a67f9d1e0049156bedfe4d61a4cf8511dc8903ba80cf297b6bffad3c2b379e`，与已索引指纹一致。客户端末题只把 `season`、答案映射及可选显示名等提交到 `POST /api/v1/results`，随后依返回的 `publicResultId` 打开结果页；结果页再通过 `GET /api/v1/results/{id}` 读取结果。静态代码显示 S1 结果视图接收 `resultType`，S2 结果视图读取每轴的 `leftPercent`/`rightPercent` 并按较大一侧绘制方向，25 个百分点差值只用于图形强度分档。客户端没有暴露从原始答案计算这些结果字段的公式。该发现只界定当前 bundle 的前端责任和字段形状，不证明 API 返回值的来源、分数公式、服务端验证或官方结果正确性；本次没有发出任何结果请求或提交答卷。

同一 bundle 的 S1 结果图还会把 `resultType` 中的六级轴代码映射为 3、2、1、1、2、3 的图形强度；S2 结果说明则称每轴最多测量 2 点，并以左右百分比绘制方向。它们描述的是两种结果视图的呈现尺度，不能当作原始答题分、题目权重或跨季可比量表。此处只检查了结果渲染分支，没有提取或保存题目正文；服务端如何从答案生成 `resultType` 或百分比仍为 `UNKNOWN`。

**可验证的低提交成本方案**：先寻找官方公开规格或获得制作方可核验规则；其次优先取得参与者主动公开、可核对来源版本且不包含私人信息的完整答案—结果对；若确需真实黑箱试验，先经动作级同意，使用匿名、明确合成的两极基准和少量单题／成组差分，逐次记录题库指纹、完整输入、公开输出与时间。每次结果可能被官方 `result-storage-v1` 接口储存，不得制造大量生产结果、绕过 Firebase App Check／reCAPTCHA、忽视速率限制或把防机器人请求当作可规避的小 Bug。用户本轮在 Chrome 中走到第二季 `37/37`、已选择前 36 道「O」，**尚未点击末题、没有 POST、没有创建官方结果**；此前另一次交互已记录过 reCAPTCHA 请求，因此不得承诺可批量重复提交。

第二季若按全部 37 个二选组合穷举，有 `2^37 = 137,438,953,472` 条答卷；这不是可接受的原站探测策略。即使未来能证明分轴加权相加，单题效应的可识别性仍需要足够多的**数值输出**及阈值附近的对照；只观察三轴 `1`／`2` 的离散标签通常不足以唯一识别权重、归一化、交互和分类阈值。对第一季 87 题也不能把第二季的评分规律直接移植。

1. 拆解每题权重、反向题、缺失答案处理、每轴归一化、阈值/分档、并列处理、最终人物或倾向标签的判定；没有来源就不设为「官方算法」。
2. 收集**经许可且同版本**的原站输入→输出金标准样例；至少有每个维度的两端、恰好在阈值上下、逆向题、平分/并列、重测时结果不变。与本站同输入差分测试并附可复现报告。
3. 对本站原创评分做性质测试：输入完整性检查、选项极性、单维度独立性、前后重复一致性、未答题不计分；小题库做全组合穷举。
4. 保留 **题库版本 + 评分版本 + 译文版本**，旧用户结果不能因升级算法静默改变。

**验收输出**：来源、可运行金标准、同输入的差异/误差、每轴与最终标签的验收记录。当前**演示版的内部一致性可测**，但原站差分测试**不可开展**。

### L4 · 真实产品：嘉宾匹配、账号和隐私

1. 只纳入可追溯的同季、同评分版本、同维度嘉宾结果，缺失值不得用虚构分数填补；测试排序、并列、不同季隔离。
2. 社交账号必须经公开来源归属核查；「最活跃」还须有跨平台可比的近期活动证据，否则仅显示「已验证公开账号」。
3. GitHub OAuth 只用于识别登录用户，写入个人结果必须明确同意、服务端隔离、可导出/删除；双账号交叉访问与删后读回均验收。
4. 访问者能在不登录的情况下完成测验，默认只在本机计算；网站清楚标注「独立非官方」。



工作流范围：`.github/workflows/verify.yml` 的 `pull_request.paths` 包含 `docs/VERIFICATION-MATRIX.md`，因此更改本文件会触发 GitHub Actions；其他文档路径（例如本目录下的嘉宾或版权研究文档）若没有同时更改触发路径，不会单独触发该工作流。实际运行仍以 PR 的 Checks 为准。

## 自动测试与人为审计的分工

- 运行 `npm test`：本站原创小型题库的题目数据、两季计分与嘉宾匹配单元测试，另有独立双季会话、源题索引、防止演示题被计数与状态标志晋级的反例，以及两季所有完整答案组合的**程序化穷举**（第一季 4^8=65,536；第二季 2^6=64）。这只能证明实现对**本站定义的演示规则**保持一致；代码和预期值同源时仍可能同时出错，需要独立金标准。
- 运行 `npm run audit:reproduction`：核查公开观察数量与本站演示数量，并始终如实显示节目原版等价状态未证实。
- 运行 `npm run check && npm run build`：Astro 类型/构建可用性；需要在真实桌面浏览器和 iPhone 18 Pro Max 440×956 CSS px 验收中文、双语顺序、结果、错误与回退路径。
- 人工/第三方审校仍是**正式翻译／原版复刻**不可省略的门槛：双语语义、原始证据、重用许可、节目规则与嘉宾公开账号归属。用户目前允许原题草稿先行试填，不等于测试通过就把上述 `UNKNOWN` 晋级成 `PASS`。

## 宣称「忠实复刻」之前的发布闸门

两季分别确认：合法可用的逐题韩文与选项完整、独立中文双语复核、完整答题状态图覆盖、可靠的官方评分规格或金标准差分通过、嘉宾可比数据真实、隐私和移动端验收通过，方可在对应范围内使用「复刻」措辞。否则只能发布明确区分的「独立创作演示版」和本次用户限定的「非官方公开原题试填／AI 初译」；两者都要公开各自缺口。
